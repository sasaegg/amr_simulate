# 17 存圖與地圖格式

檔案：[`warehouse_small.yaml`](../../docker/amr_sim/data/maps/warehouse_small.yaml)、[`warehouse_small.pgm`](../../docker/amr_sim/data/maps/warehouse_small.pgm)、[`amr.urdf.xacro`](../../ros_ws/src/amr_description/urdf/amr.urdf.xacro)（輪子碰撞）

子專案 2 task 2.3（使用者以 teleop 建圖並存圖），以及建圖時發現的車輛模型問題。

## 為什麼要做

建圖的結果要存成檔案，之後導航（map_server）載入、子專案 3 的網頁顯示、子專案 4 標儲位都用同一張圖。Nav2 的標準格式是一張灰階圖片 + 一個描述檔。

## 做了什麼

### 存圖

```bash
ros2 run nav2_map_server map_saver_cli -f /data/maps/warehouse_small --ros-args -r map:=/amr1/map -p use_sim_time:=true
```

- map_saver 訂閱 `map`（預設 `/map`），收到一張就存檔結束；我們的地圖在 namespace 下，所以 remap。
- 存檔不需要停止建圖，隨時可以存一版。

### `.yaml`：描述檔

```yaml
image: warehouse_small.pgm      # 圖片檔（相對於這個 yaml）
mode: trinary                   # 三值：佔據／空曠／未知
resolution: 0.05                # 每個像素 0.05 m
origin: [-1.13, -1.11, 0]       # 圖片「左下角」像素在 map 座標系的位置 [x, y, yaw]
negate: 0                       # 0：白＝空曠、黑＝佔據；1 反過來
occupied_thresh: 0.65           # 佔據機率 > 0.65 算佔據
free_thresh: 0.25               # 佔據機率 < 0.25 算空曠，中間算未知
```

- **origin 是左下角**，不是圖片中心也不是車子位置。這張圖 origin = (-1.13, -1.11)：建圖從車在 (0, 0)（地圖座標）開始，牆在車的左後方約 1.1 m 處，所以圖片的左下角在 (-1.13, -1.11)。之後以「標地圖原點」把原點改到倉庫左下角，origin 變成 (−0.13, −0.11)（圖片不變，見[筆記 25](25-標地圖原點.md)）。
- 換算：像素 (col, row) → 地圖座標 `x = origin_x + col × res`、`y = origin_y + (height - 1 - row) × res`（圖片的 row 由上往下，地圖的 y 由下往上）。子專案 3 的網頁畫地圖時會用到。

### `.pgm`：圖片

PGM（Portable GrayMap）是最簡單的灰階圖片格式：檔頭 `P5`、寬高、最大值 255，後面是每個像素一個 byte。trinary 模式存出的值：

| 像素值 | 意義 | ROS OccupancyGrid |
|---|---|---|
| 254（白） | 空曠 | 0 |
| 0（黑） | 佔據 | 100 |
| 205（灰） | 未知 | -1 |

這張地圖：404 × 305 像素（20.2 × 15.3 m）；空曠 112856、佔據 4530、未知 5834（4.7%，大多在牆外）。四面牆、六個貨架、隔間牆、東區短牆、兩個箱子、兩個圓柱都清楚，東北房間也掃到了。

`.gitattributes` 已把 `*.pgm` 標成 binary，git 不會改它的換行。

### 地圖存放位置

`docker/amr_sim/data/maps/`（使用者決定放在 `docker/amr_sim/` 底下，和 compose、config 同一處），compose 以 `./data:/data` 掛載到 robot 容器。地圖納入 git，clone 下來不用重建就能導航。

## 建圖時發現：輪子碰撞形狀讓 odom 漂移

開發時用腳本沿路徑點自動建圖，第一張地圖**疊成好幾份、每份轉了不同角度**。

排查過程：
1. 記錄 slam_toolbox 的修正量 `map → odom`：第一段直線就偏 8.6°，越來越大到 -56°。在模擬中 odom 理應很準，修正量應該接近 0。
2. 直接問 Gazebo 車子的真實位置（`ign model -m amr1 -p`）：真實在 (11.5, 0.3)，odom 以為在 (1.0, 1.1)——**odom 錯了，SLAM 其實在努力修正它**。
3. 對照實驗（odom 變化量 vs 真實變化量）：

| 動作 | odom | 真實 |
|---|---|---|
| 直線 8 s | 2.80 m、0° | 2.80 m、0° |
| 原地轉 5 s | 172° | 189° |

直線完全對，只有轉向多轉約 10%。odom 用「兩輪速度差 ÷ 輪距」算角速度，輪距參數 0.44 m（兩輪中心距離）。實際轉得快 10% ⇒ 物理上的有效輪距約 0.40 m，正好是**兩輪內側邊緣**的距離。

原因：輪子碰撞形狀是圓柱。物理引擎算圓柱和地面的接觸時，接觸點常落在圓柱的邊緣（輪緣），而不是輪寬中央。

修正：碰撞形狀改成**球**（半徑 = 輪子半徑），外觀（visual）仍是圓柱。球和平面只有一個接觸點，而且在輪子中心平面上，有效輪距就等於參數。

```xml
<collision>
  <geometry><sphere radius="${wheel_radius}"/></geometry>
</collision>
```

改完：直線、原地旋轉、各種半徑的弧線，odom 和真實值完全一致；自動建圖整趟 `map → odom` 都在 4 cm、0.4° 以內，地圖乾淨。加了兩個測試：URDF 檢查碰撞是球；`test_sim_smoke` 的 test_10 比對原地旋轉時 odom 與 Gazebo 真實航向（把輪子改回圓柱時，這個測試會失敗：1.81 vs 1.98 rad）。

**真車沒有球形輪子**——這是模擬的建模技巧。真的輪胎有彈性，接觸面在輪寬中央附近；物理引擎的剛體圓柱做不到，球形碰撞反而比較接近真實的接觸行為。真車上 odom 的誤差來源不同（輪徑誤差、打滑、地面不平），要靠校正（實際量測轉一圈的角度、走一段的距離，反推有效輪距與輪徑）和感測器融合（IMU、SLAM）處理。

### 其他人怎麼解（2026-10-08 查證）

- **Articulated Robotics**（ROS 2 常被引用的差速車教學）在 Gazebo 章節最後一步就是把驅動輪的碰撞改成球，理由是接觸點變成一個極小的點，減少差速運動的摩擦造成的 odom 問題；同時把支撐輪摩擦設為 0——和我們的做法一致。
- 也有反向的經驗：用 STL 網格當輪子碰撞會接觸不穩、車子抖動，換成圓柱就好（mir_robot）。所以是「網格 < 圓柱 < 球」的層次，不是圓柱不能用。
- 其他模擬器也有類似現象：Isaac Gym 用圓柱／膠囊輪時接觸點異常、輪速亂跳、漂移（NVIDIA 論壇，未見解法）。
- 替代做法：把 `wheel_separation` 調成實測的有效值（0.40）——odom 會準，但參數和車輛尺寸不一致，換真車容易出錯；調摩擦／接觸參數（`mu1`、`mu2`、`kp`、`kd`）——可減輕抖動，但不保證接觸點回到中央。都不如球形碰撞直接。

**哪些是確定的、哪些是推論**：實測數據是確定的（改前 172° vs 189°、改後 173.0° vs 173.0°，5 種弧線一致，回歸測試在圓柱時失敗）；「接觸點落在輪子內緣」是由數字反推（多轉 10% ⇒ 有效輪距約 0.40 m ＝ 兩輪內緣距離），沒有在 Gazebo 把接觸點畫出來直接觀察。

**副作用**：球直徑 0.16 m，比輪寬 0.04 m 寬，兩側各多出 6 cm 的碰撞範圍（車身側面貼著障礙物時可能較早碰到；導航 costmap 用實際車寬加膨脹距離，影響不大）。球不代表真實輪胎形狀，要模擬不平地面、側滑時需要更細的輪胎模型。

## 面試追問

**Q：Nav2 的地圖檔格式？**
A：一張灰階圖片（pgm／png）加一個 yaml：解析度、左下角原點、佔據與空曠的門檻、是否反相。map_server 讀進來轉成 OccupancyGrid（0 空曠、100 佔據、-1 未知）。

**Q：為什麼 map 座標系的原點不是世界原點？**
A：SLAM 不知道「世界」，只能以開始建圖時的位置當原點。真實部署時通常在建圖後再定義原點或對齊到建築座標（或在地圖上標出儲位、充電站的位置）。

**Q：odom 不準怎麼排查？**
A：拿可信的參考（模擬用 ground truth；真車用量尺、動作捕捉或繞一圈回原點）分別測直線與旋轉。直線錯通常是輪徑，旋轉錯通常是輪距；也要排除打滑（車被卡住時輪子空轉，odom 照樣累加）。

**Q：模擬和真實的差距（sim-to-real gap）你遇過什麼？**
A：剛體圓柱輪的接觸點落在輪緣，讓有效輪距變小、odom 航向漂移，SLAM 地圖扭曲。修正是用球形碰撞讓接觸點回到中央；同時加了 odom 對 ground truth 的回歸測試，避免之後改模型又壞掉。

## 踩坑紀錄

- **odom 錯但 SLAM 被誤會**：一開始以為是 SLAM 參數問題；記錄修正量、再拿 Gazebo 真實位置比對，才發現是 odom。
- **開發腳本以 odom 判斷到達**：車子卡在牆邊輪子空轉時，腳本還以為一直有在前進。之後驗證位置一律用 Gazebo 真實值。
- **輪子改球後仍看到弧線有 9% 誤差**：那次車子剛好碰到障礙物、部分卡住；換到空曠處重測 5 種半徑都完全一致。
