# 11 世界與車子系統分離（三個 launch）

檔案：[`world.launch.py`](../../ros_ws/src/amr_worlds/launch/world.launch.py)、[`robot.launch.py`](../../ros_ws/src/amr_bringup/launch/robot.launch.py)、[`sim_hardware.launch.py`](../../ros_ws/src/amr_hw_sim/launch/sim_hardware.launch.py)、[`spawn.py`](../../ros_ws/src/amr_hw_sim/amr_hw_sim/spawn.py)、[`compose.yaml`](../../docker/amr_sim/compose.yaml)、[`config/`](../../docker/amr_sim/config/)

> **2026-10-08 更新**：三個 launch 已改為 XML，`world.yaml`／`robot.yaml` 與設定合併程式已刪除，設定改為 launch 參數（見[筆記 14](14-launch改為XML.md)）。本篇的架構（兩個容器、硬體模式、spawn 生命週期）不變，下面的 `.launch.py` 與設定檔是當時的寫法。

## 為什麼要做

第一版（task 5.4）用一個 `sim.launch.py` 同時啟動 Gazebo、生成車輛、bridge、robot_state_publisher、watchdog——世界與車子系統混在一起，到了真車上無法直接沿用。架構調整（2026-10-08）以「真車」為準重新劃分：

```
┌──────────────── robot 容器（車子系統：之後部署到真車）────────────────┐   ┌──── sim 容器 ────┐
│ robot.launch.py（中控）  hardware: sim | real                           │   │ world.launch.py  │
│  ├ robot_state_publisher（與硬體無關）                                 │   │  ├ Gazebo 世界   │
│  └ hardware: sim → sim_hardware.launch.py（虛擬驅動）                   │◀─▶│  └ /clock bridge │
│       ├ 虛擬底盤  spawn、cmd_vel_watchdog、base bridge                   │gz │  （沒有車輛）     │
│       ├ 虛擬光達  lidar bridge                                          │   └──────────────────┘
│       └ 虛擬 IMU  imu bridge                                            │     真車上不存在
│    hardware: real → 真車驅動（尚未提供，報錯）                          │
└────────────────────────────────────────────────────────────────────────┘
```

**硬體介面**：虛擬驅動提供的 topic（`/amr1/cmd_vel`、`scan`、`odom`、`imu`、`joint_states`、`/tf`）和真車驅動一樣。上層（之後的 SLAM、Nav2）不需要知道下面是模擬還是真車——這就是硬體抽象層（HAL）。

## 設計討論中的關鍵問題

**光達由 Gazebo 算，不是怪怪的嗎？車子「實際」可能在別的地方？**
模擬裡 Gazebo 就是真實世界，只有一個「車子實際的位置」。真實光達是物理裝置，從車子**真正所在的位置**量測，不管軟體以為自己在哪裡；gpu_lidar 也是從 Gazebo 裡的位置量測——兩者一致。若反過來從「車子以為的位置（里程計）」算 scan，定位誤差永遠不會被發現（循環論證）：定位演算法正是拿「感測器實際看到的」與「依自己的估計應該看到的」比較來修正位置。模擬的額外好處是 Gazebo 知道真實位置（ground truth），可以量化定位誤差。

**車子位置應該由誰決定？**
真車開機時，位置由物理世界決定（有人把車推到某處），車子系統只能「估計」。模擬中「把車放進世界」對應「把車推到出生點」，在新架構裡是虛擬底盤啟動時做的事，位置寫在 robot 側的 `robot.yaml`（`sim.spawn`）。世界（場景 YAML）不再知道有哪些車——出現 `spawn` 欄位時報錯。車子系統啟動時認為自己在 odom 原點；子專案 2 的 SLAM／AMCL 再提供 `map → odom`。

**watchdog 放哪一側？**
真車的馬達驅動板本身有指令逾時；DiffDrive 沒有，所以 watchdog 是「假驅動板」，屬於虛擬驅動。`cmd_vel_gz` 只存在於模擬側。

**中控是 launch 還是常駐的監控節點？**
先做 launch（依模式一次帶起），感測器健康檢查、重啟、lifecycle 之後再加。

| `amr_description` | 車輛 xacro | ✅ |
| `amr_worlds` | 場景產生器、world、`world.launch.py` | ❌ |
| `amr_bringup` | 中控 `robot.launch.py` | ✅ |

## 設定：三個檔案

```
docker/amr_sim/config/
  ros.env      兩個容器共用（compose env_file）：ROS_DOMAIN_ID
  world.yaml   sim：world、headless
  robot.yaml   robot：robot_id、hardware（必填）、sim.spawn
```

- 三層覆寫：套件預設 ← 設定檔 ← 命令列；命令列空字串＝沒給；未知的鍵報錯（打錯字不默默忽略）。
- **`hardware` 沒有預設值**：避免真車誤以模擬模式啟動或反之。
- `use_sim_time` 由 `hardware` 決定（sim → true），不另設，避免兩個設定矛盾。
- robot_id 只在 robot 側——世界不知道有哪些車，所以「兩邊 id 要一致」的問題不存在。
- **移除 `AMR_WORLDS_DIR`**：world 從套件 share 目錄讀。`--symlink-install` 下修改既有檔案即時生效；新增檔案需要 `colcon build`（錯誤訊息會提示）。

## 三個 launch

**OpaqueFunction**：launch 檔是「先描述、後執行」；`generate_launch_description()` 被呼叫時參數還沒有值（只是 `LaunchConfiguration` 占位符）。要拿參數值去讀檔、合併、計算，必須在 `OpaqueFunction` 裡用 `.perform(context)` 取值。

- `world.launch.py`：`ign gazebo -r <world>`（headless：`-s --headless-rendering`，EGL 離屏渲染，光達照常）＋ `/clock` bridge。
- `robot.launch.py`：xacro 展開 → robot_state_publisher（namespace、`frame_prefix: amr1/`）；sim 時 `IncludeLaunchDescription` 虛擬驅動並傳入 robot_id 與出生點；real／缺 hardware → 例外，`ros2 launch` 結束碼 1。
- `sim_hardware.launch.py`：spawn、watchdog、三個 bridge 節點（`name=<元件>_bridge`、`namespace=amr1`）。

## spawn 的生命週期（實測踩出來的）

```
等待世界（ign service -l 找 /world/<名稱>/create；逾時報錯）
  ├ 世界中沒有 amr1 → ros2 run ros_gz_sim create -string <URDF 內容> → 確認出現，否則重試
  └ 已有 amr1（前一次車子系統停止後留下的車體）→ 送一次零速度 → set_pose 移回出生點 → 確認到位
```

- **create 回 OK 不代表成功**：世界剛起來時要求會被丟掉、同名實體已存在時也回 OK → 用 `ign model --list` 確認，沒有就重試。
- **不能用 `-file`，要用 `-string`**：`-file` 只傳路徑，Gazebo 在 sim 容器讀檔，暫存檔在 robot 容器 → `Unable to read file`。同一個容器測試時兩邊共用 `/tmp`，問題被藏起來；分成兩個容器才暴露。
- **不移除再生成，改用 set_pose**：Fortress 移除同時帶 gpu_lidar 與 IMU 的模型後，場景服務會壞掉（模型清單查不到、之後無法生成；只有其中一種感測器時正常）。原設計是「先移除再生成」，因此偏離——世界中仍只有一台、位置與朝向正確；差別是 DiffDrive 的里程計接續之前的數值（odom 是相對座標系，起點不影響正確性）。
- **移回前先送零速度**：DiffDrive 會一直執行最後一筆指令，否則移回後車子接著跑。
- `ign model` 沒有指定 world 的參數（只支援單一世界）；世界多於一個時 spawn 報錯。

## compose 與腳本

- `sim`、`robot` 兩個 service、同一個映像（build 只寫在 sim）；兩者都有 GPU、X11（robot 之後跑 RViz）、`ipc: host`、`ros.env`。
- `compose.software.yaml` 對兩者都 `deploy: !reset {}`。
- `up_gpu.sh`／`up_cpu.sh` 啟動兩個；`exec.sh <sim|robot>` 必須指定，沒給或給錯顯示用法並以結束碼 2 結束。

日常流程：

```bash
docker/amr_sim/up_gpu.sh
docker/amr_sim/exec.sh sim     # ros2 launch amr_worlds world.launch.py config:=/config/world.yaml
docker/amr_sim/exec.sh robot   # ros2 launch amr_bringup robot.launch.py config:=/config/robot.yaml
docker/amr_sim/exec.sh robot   # 另開：teleop、RViz
```

| 項目 | 結果 |
|---|---|
| 世界啟動後 | 只有 `warehouse`；`/clock` 1 個發布者 |
| 車子系統啟動（robot.yaml） | 車輛出現在 (1, 1)；6 個節點；scan 10、odom 29.4、imu 100 Hz |
| `hardware: real`／未設定 | 結束碼 1，訊息分別為「尚未提供真車驅動」「必須明確設定，可用值 sim, real」 |
| 開車中途 robot Ctrl+C | robot 0 殘留；Gazebo 與車體仍在；車停在原地 |
| 再次啟動車子系統 | 停下並移回 (1, 1)，只有一台 |
| 先啟動驅動、5 秒後才啟動世界 | 等待後成功生成 |
| 不同出生點重啟 (3, 1, π/2) | 位置 (3.0, 1.0)、朝向 1.5708 |
| 新增 world 未 build | 錯誤訊息提示 colcon build；build 後可載入 |
| `ROS_DOMAIN_ID=42` | 兩容器皆 42、robot 收得到 scan；以 domain 0 查看看不到 |
| 車輛介面 | 只有 `/amr1/*` 與全域 `/tf`、`/tf_static`、`/clock`；TF 含輪子；從 1.0 m/s 停送 0.86 s 停車；送 5.0 m/s 實際 1.0 |

測試工具（非產品程式）：非互動 shell 的背景工作會忽略 SIGINT（子程序繼承），所以測試時用小工具在 exec 前把 SIGINT 恢復成預設，才能模擬 Ctrl+C；`pkill -f` 會比對到執行它的 shell 自己。

## 面試追問

**Q：模擬和真車怎麼共用同一套程式？**
A：分成車子系統與世界。車子系統的中控依 `hardware` 帶起虛擬或真實驅動，兩者提供相同的 topic（硬體介面），上層不知道差別。車子系統套件不依賴任何模擬套件，虛擬驅動只在 sim 模式於執行期依名稱載入。

**Q：模擬的光達根據什麼算？為什麼不用車子估計的位置？**
A：根據車子在模擬世界中的實際位置，跟真實光達一樣。若用估計位置算，定位錯誤就永遠發現不了，因為定位就是靠比較「看到的」與「預期看到的」來修正。

**Q：兩個容器怎麼溝通？踩過什麼坑？**
A：host 網路的 DDS（加 `ipc: host` 共用 shared memory）與 Gazebo transport。坑：spawn 用 `-file` 傳暫存檔路徑，Gazebo 在另一個容器讀不到，要用 `-string` 傳內容——檔案系統不共用時，任何「傳路徑」的介面都要小心。

**Q：launch 檔為什麼要用 OpaqueFunction？**
A：launch 先建立描述、再執行；參數在描述階段只是占位符。需要依參數值讀檔、計算時，必須在 OpaqueFunction 裡於執行期取值。

**Q：為什麼 hardware 沒有預設值？**
A：模式選錯的後果嚴重（真車以為自己在模擬、或模擬去找真驅動），寧可沒設定就報錯，強迫明確選擇。

**Q：遇到第三方軟體的 bug 怎麼處理？**
A：先最小化重現並縮小範圍（只有光達、只有 IMU、兩者都有），確認是上游問題後找替代路徑（set_pose 取代移除＋生成），把原因與限制寫進設計文件，之後升級版本時再評估。

## 踩坑紀錄

- 測試時使用者稍早用 GUI 啟動的舊版模擬還在跑，`/clock` 出現兩個發布者——先確認環境乾淨再測。
- `ign model --list -w <world>`：沒有 `-w` 參數，輸出為空 → 誤判車輛不存在。
- create 回 OK 但沒有生成（世界剛起來、或同名已存在）→ 生成後確認、重試。
- 移除帶 gpu_lidar＋IMU 的模型讓 Fortress 場景服務損壞 → 改用 set_pose。
- DiffDrive 執行最後一筆指令 → 移回前先送零速度；watchdog 結束時直接以 ign topic 送零速度。
- `-file` 跨容器讀不到 → `-string`。
